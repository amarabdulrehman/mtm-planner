// How it works

// Guarantees

Stays correct when
the messages change.

Real event planning is a stream of corrections. Prices go up, halls close, someone without authority asks for less food. The planner handles all of it.

Wrong messages are caught

A sender without authority, an out-of-date price, or a change that leaves people hungry is rejected with a plain reason. The last good plan stays in place.

Latest decisionMessage rejected

100 meals would leave 36 of 136 people without lunch. Only the organiser can change the meal order.

Newest message wins

Facts carry their sender and date. When the caterer's rate changes, the old one is superseded and every total that used it updates.

[superseded] #5 Caterer: biryani box
Rs 700 → Rs 850 per head (replaces #4)
[superseded] #9 Hall 3 under maintenance
[ignored] #10 Library closing early

Every call on the record

Model, area, input, output and tokens for every call. Download the plan and the full trace as one file.

One command, every time

The same command for the first run and every update. A new message uses at most 5 model calls, usually 1.

$ npm run plan -- messages.txt
✓ 7/7 checks · 2 calls · 4.4 s

Replies drafted, never sent

Each sender gets a reply on the channel they used. A person always presses send.
